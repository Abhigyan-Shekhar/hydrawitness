# HydraWitness Codex MCP integration

`hydrawitness.mcp_server` exposes four stdio MCP tools. `verify_evidence` assesses a claim, `trace_sources` shows its evidence paths, `scan_impact` previews reassessment targets, and `assess_and_improve` writes graph repairs over at most five iterations. The first three tools are read-only. Server configuration specifies the registry and graph scope. Policies are allowlisted. Decisions are advisory. Treat artifact text as untrusted evidence. Root verification reflects assertions in fixture metadata.

For a claim populated by the local [GitHub Actions import](../README.md#github-actions-observations), `verify_evidence` and `trace_sources` return commit-bound workflow observations in `provenance.workflow_evidence`. Run the MCP server with the same scope used for import. The observations carry GitHub's run IDs, attempt numbers, conclusions, and source URLs. Release policies continue to evaluate mandatory security scans using their own required relationships.

For a claim populated by [GitHub Actions security scan import](../README.md#github-actions-security-scans), `provenance.sources` includes the run and required scan with their GitHub URLs, commit, run attempt, job, and step identifiers. The assessment compares the scan subject to the release subject, and `scan_impact` can look up dependent claims using the returned scan ID.

Call `scan_impact` with `{"scan_id": "demo/scan"}` after the demo investigation. Each impacted claim has `status: "REASSESSMENT_REQUIRED"` and a shortest dependency `path`. The path lists actual directed edges in claim-to-scan order. The first `SUPPORTS` edge points from the supporting source to the claim, followed by any `DERIVED_FROM` edges and the `REQUIRES` edge into the scan. Matching uses the scan's and claim's exact stored subjects.

The repository-scoped `.codex/config.toml` starts the local virtualenv server. According to [OpenAI's configuration documentation](https://learn.chatgpt.com/docs/config-file/config-basic), project config loads only for trusted projects. Install the dependency and set `HYDRAWITNESS_SCOPE` to a scope seeded by `python -m hydrawitness.seed_codex` before starting Codex. `HYDRA_URL` and `HYDRA_TOKEN` can be supplied via environment; do not commit credentials. The sample token is for the local disposable instance only. See [OpenAI's MCP configuration documentation](https://learn.chatgpt.com/docs/extend/mcp?surface=cli).

The actual CLI trace files in `demo/` document two separate sessions against the same persisted scope. Session one called verify then improve and changed `REVIEW_REQUIRED` to `BLOCK`; session two called verify on a related claim and observed `BLOCK` without an ingestion call. Waggle memory-tool events were removed from these captured JSONL files; HydraWitness tool events and agent messages are unchanged. Those captures used two source reports; the later dashboard fixture uses four. Run the protocol integration test with `.venv/bin/python -m unittest tests/test_mcp_protocol.py -v`.

Current limitations: no general claim extraction, no production identity/authentication, no concurrent-writer transaction protection, no trust or signature verification, and a narrow release-policy model. The service is advisory; it cannot deploy or merge anything. Never expose the development HTTP database or dashboard publicly.
