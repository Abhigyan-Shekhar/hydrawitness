# Evaluation protocol — synthetic v1

Use revision `6383373` to reproduce the historical decision policy described here. The frozen fixtures omit release identities. The current engine sends unbound mandatory scans to review, so its results can differ from these historical labels and measurements.

Run `python3 -m evals.run --output-dir /tmp/hydrawitness-eval` with the local HydraDB container available. To reproduce the second deterministic ordering, use `python3 -m evals.run --seed 1 --output-dir /tmp/hydrawitness-eval-order-1`. These commands add new, randomly scoped data to the existing database. Repeated runs accumulate data. Output files are overwritten within the chosen output directory. HydraDB errors, incomplete pages, split failures and checksum mismatches cause a nonzero exit.

## Data and isolation

`datasets/benchmark/` contains 21 synthetic artifacts, 40 learning questions, 20 held-out questions and a separate gold file. The dataset is versioned and its exact artifact, question and gold files are recorded in `checksums.json`; the runner checks both hashes and the file set. Gold decisions and root sets were frozen before the first run of this benchmark. The underlying ten scenario patterns and their expected decisions were adapted from the earlier hand-authored test fixtures; the labels therefore are not independent expert adjudications.

There are ten evidence groups, with two differently worded held-out questions per group. Eight groups have five learning questions each. Two groups (stale and missing reference) have no learning questions and measure whether unrelated graph repairs change their results. The question wording is descriptive: the current engine is invoked with a preselected claim and sources, not natural-language understanding. Both held-out questions in each group use the same source and policy, so they are correlated; the effective diversity is much closer to ten groups than twenty independent cases.

All initial claims and source nodes are seeded into a fresh random ID scope before baseline measurement. Learning and held-out questions within an evidence group intentionally share source IDs. The engine sees artifact files, learning questions and a policy for each invocation; it never receives held-out gold labels. The evaluator reads gold only to score returned predictions, never to decide learning actions. Evaluation uses `Witness.assess` within a read-only guard that rejects mutating query forms. Learning uses `Witness.improve` only on learning claims. This guards the application's queries, not a database-level read-only account. The clock is fixed to 2026-11-14 12:00 UTC for reproducible age judgments.

`root_verified` is a trusted synthetic fixture assertion, not independently verified provenance. Gold roots are expected root sets for these controlled records. Cycle, stale and missing-ancestor cases correctly expect no verified roots where the contributing lineage is incomplete. Scan failures block only under policies requiring scans; missing scans require review. A failed scan under a policy that does not require one is reported as a contradiction and causes review.

## Comparators and metrics

- **Flat:** reads the same initially attached source documents from HydraDB, treats each fresh document as an independent confirmation and checks directly attached security-scan documents. It does not follow citations, derive roots, or perform repairs. It applies the same policy's required-scan, freshness and minimum-confirmation conditions, but its independence assumption is intentionally naive. Its root-set score is its document-as-root guess. It is deterministic and not an LLM baseline.
- **Static graph:** uses the same seeded graph and policy evaluator as the candidate, without any active ingestion. Its held-out results at iteration 0 are used as the constant baseline.
- **HydraWitness:** uses the same evaluator, and processes learning questions in batches of ten, resolving only referenced gaps. Held-out assessments are read-only at every checkpoint. Its curve reflects changes to the stored graph, not online held-out repair.

Exact accuracy uses 20 held-out decisions as denominator. False approval is the fraction of gold `BLOCK` or `REVIEW_REQUIRED` questions predicted `APPROVE`. Correct-review rate uses the gold `REVIEW_REQUIRED` subset as denominator. Root accuracy requires exact equality with the gold verified-root set for each question. Open gaps count gap records across all questions, so common gaps can be counted more than once. Counts of new sources and relationships include only repair actions, not seed writes or improvement-history nodes and edges. Query counts and nearest-rank p50/p95 measure client-side end-to-end HydraDB request elapsed time, including HTTP and local scheduling; they are not server execution times or a load test.

## Results and interpretation

The frozen-order run in `evals/results/` observed 10/20, 14/20, 14/20, 16/20 and 20/20 across checkpoints; the static graph remained at 10/20 and flat scored 6/20 with 6/14 false approvals. The seed-1 order in `evals/results-order-1/` observed 10/20 then 20/20 at every subsequent checkpoint. This order saw all relevant repairable groups in its first batch; it is an ordering sensitivity demonstration, not a statistical confidence interval. In both runs the final 10 improvements are five pairs of related questions changing from review to the labeled block or approve decision. The unrelated held-out groups did not change.

The main mechanism is discovering existing but initially unavailable artifacts and inserting the associated graph relationships. A subsequent [artifact-only ablation](ablation-report.md) matched the full graph on decision and root accuracy when it had the same available artifacts and could resolve their recorded references; persisted edges did not add measurable decision accuracy on this set. They do not establish generalization to unrelated organizations or document types, and the small, highly templated dataset is not a production accuracy estimate. No model-based baseline, statistical significance, or production-scale performance is claimed.

## Profiling and limitations

The default run recorded 1,284 total HydraDB requests, including 354 seed requests. Its four learning batches issued 145, 45, 95 and 101 requests; the five held-out graph assessments issued 88, 100, 100, 104 and 112 requests. The most frequent shapes were 249 `DERIVED_FROM` adjacency reads and 249 `REQUIRES` reads. The assessor revisits shared ancestry independently per supporting document and per held-out claim, and the writer checks nodes and edges individually. No cache or batching optimization has been claimed without an isolated before/after performance experiment. The preserved runs overlapped briefly with other local test activity, so their latency figures are indicative only, not controlled performance measurements.

The flat baseline has no way to discover an unattached scan; its conservative review behavior for scan-required policies differs from a hypothetical generative baseline. Gold decisions use this prototype's narrow policy semantics, and contradictory report content outside explicit scan outcomes is not modeled. Evidence freshness uses fixture timestamps; artifact source authority, supersession, trust adjudication and richer claim semantics remain future work. The database uses deterministic scoped IDs but lacks multiwriter isolation and cryptographic content authentication. The legacy fixed-ID proof is separate and must not be used as the evaluator.
